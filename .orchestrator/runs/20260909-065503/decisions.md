## D11 · 인라인 폴백을 쓰지 않기로 번복 (D6·D7 부기를 대체)

- **이유**: 스폰 직전에 양쪽 정의를 **구조 검사**로 대조했더니 결과가 동일했다.

  실습02/implementer.md   경계 6/6 OK  tools=Read, Edit, Write, Bash, Glob, Grep

  테스트01/implementer.md  경계 6/6 OK  tools=Read, Edit, Write, Bash, Glob, Grep
  ```
  역할·안전경계·도구가 전부 일치하므로 "어느 정의가 쓰이는지 불확실하다"는 D6·D7 부기의
  전제가 사라졌다. 그리고 등록본을 쓰면 **`tools` 제한이 하드 제약으로 유지된다** —
  인라인 폴백은 이것을 프롬프트상의 약속으로 격하시킨다.
  `test-author`가 `Edit`를 갖지 않는 것은 이 주행에서 특히 중요하다. 그것이 구현자의
  자기채점을 막는 유일한 기계적 장치이기 때문이다.
- **대안**: 인라인 폴백(도구 제한 상실) / 등록 대기 후 작업공간 정의로 스폰
  (몇 분 대기 + 여전히 이름 충돌 모호성 남음).

- **되돌리려면**: 작업공간 정의를 지우고 등록본만 쓰거나, 반대로 등록본을 무시하고

## D8 · 병렬 계획: test-author는 순차, 구현 2조각은 병렬
- **결정**: 3단계로 간다.
  - S0 (오케스트레이터 직접): `lib/types.ts` — 공유 계약을 내가 쓴다
  - S1 (순차, 1스폰): `test-author` — 테스트 파이프라인 + 테스트 전량
  - S2 (병렬, 2스폰): `implementer`×2 — 백엔드 조각 ∥ 프론트엔드 조각
- **병렬 5조건 점검 (S2)**:
  1. 쓰기 영역 분리 — 백엔드는 `lib/*.ts`+`app/api/analyze/route.ts`, 프론트는
     `app/page.tsx`+`app/components/*`. 교집합 공집합. 스폰 전 스크립트로 기계 검사한다.
  2. 순서 의존 없음 — 둘 다 내가 S0에서 고정한 `lib/types.ts`만 바라본다.
     **서로를 바라보지 않는다**는 것이 핵심이다.
  3. 독립 검증 가능 — 백엔드는 `npm test`, 프론트는 `tsc --noEmit`+브라우저 렌더.
  4. 조각 2개 ✓
  5. 동시 스폰 2개 ≤ 3 ✓
- **병렬화하지 않은 것과 사유**:
  - `test-author`를 구현과 병렬로 돌리지 않았다 — 테스트가 먼저 있어야 구현자가 맞춰 쓴다.
    동시에 돌리면 구현이 끝난 뒤 테스트가 도착해 "만든 것에 맞춘 기준"이 될 위험이 있고,
    이는 D5에서 `test-author`를 분리한 이유 자체를 무효화한다.
  - `lib/types.ts`를 조각에 맡기지 않았다 — 두 조각이 **공유하는 자원**이다.
    조각에 맡기면 인터페이스 조율이 필요해지고, 그 순간 병렬 조건 2가 깨진다.
    공유 자원은 오케스트레이터가 직접 쓴다는 원칙 그대로다.
- **되돌리려면**: `git checkout <계획완료 체크포인트> -- lib app` 후 순차로 재주행.

## D10 · UI 검증을 브라우저 + fetch 스텁으로 한다
- **결정**: 프론트엔드 수락 기준(B1~B6, B8)은 dev 서버를 띄우고 브라우저에서
  `window.fetch`를 스텁으로 갈아끼워 각 응답 시나리오를 주입해 확인한다.
- **이유**: (1) jsdom/RTL을 설치할 수 없다(D2). (2) 실제 분석을 눌러 확인하면 유료 호출이
  발생한다(D4). (3) 코드를 `grep`으로 확인하는 것은 명세 게이밍을 못 잡는다 —
  "섹션이 있는가"는 문자열이 아니라 **렌더 결과**로 판정해야 한다.
- **주의**: fetch 스텁은 **검증 기법이지 제품 코드가 아니다.** 앱에 목 모드를 넣지 않는다.
- **대안**: 스크린샷 육안 확인만(문자열 존재를 기계적으로 못 박지 못해 보조 수단으로만 사용).
- **되돌리려면**: 해당 없음 (검증 방식일 뿐 산출물에 영향 없음).
