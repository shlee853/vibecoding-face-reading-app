### ★ 외모 평가 가드레일

"어떤 이성과 잘 어울리는지"는 자칫 *"당신은 이 정도 외모의 사람과 어울린다"*로 흐르기 쉽다.
그래서 프롬프트에 **실제 지시문**으로 가드레일을 넣었다. 오케스트레이터가 전문을 읽고 판정했다.

들어간 원칙: 성향·분위기·태도로만 묘사(좋은 예/나쁜 예 제시) / 외모 우열·등급 표현 금지
(금지 표현을 구체적으로 열거) / **성별 단정 금지**(요구하지 않았는데 구현자가 스스로 넣었다) /
단정적 예언이 아닌 경향형 표현 / 재미 목적 명시.

### 카메라 입력 (P2)

`getUserMedia`로 촬영해 분석할 수 있다. 업로드/카메라 탭으로 고르고, 어느 쪽이든 같은
`preview`로 합류해 이후 흐름은 동일하다. 권한 거부·장치 없음·미지원을 구분해 안내하고
업로드로 돌아가는 경로를 준다.

**스트림 정리**를 세 지점에서 한다 — `useEffect` cleanup / 촬영 완료 / 취소.
추가로 `getUserMedia`가 resolve되기 전에 언마운트되는 경쟁 조건까지 막았다(구현자 판단).
안 끄면 카메라 표시등이 계속 켜져 있는, 사용자가 감시당한다고 느낄 수 있는 실제 문제다.

철회했다** — 가드레일 근접성 검사를 만들었다가 "사실상 다른 테스트와 동치인 패딩"임을
깨닫고 지웠다고 보고했다. 이런 자기 신고가 이 구조의 핵심이다.

   구현자가 회귀를 피하려고 기존 동작을 건드리지 않은 결과다. 의도적이지만 **일관성은 없다.**

### 1. 실제 카메라 하드웨어 확인
브라우저 검증은 `getUserMedia`를 **가짜 캔버스 스트림으로 대체**해서 했다. 흐름·오류 분기·
스트림 정리는 이것으로 진짜 검증됐지만, 아래는 확인하지 못했다:
- 실제 웹캠에서의 화질·해상도 (검증 중 가짜 스트림은 2×2로 잡혔다)
- 모바일에서 `facingMode: 'user'`가 전면 카메라를 고르는지
- 브라우저별 권한 요청 UI 차이
- **HTTPS 제약** — `getUserMedia`는 보안 컨텍스트를 요구한다. `localhost`는 되지만
  **배포 시 HTTPS가 아니면 카메라가 아예 안 뜬다.**

**하는 법**: `npm run dev` 후 카메라 탭을 눌러 실제로 찍어보세요.
